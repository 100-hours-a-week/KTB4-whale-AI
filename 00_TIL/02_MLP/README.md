# 260609 회고록

- (현상) `ValueError: shapes (2,1) and (2,2) not aligned: 1 (dim 1) != 2 (dim 0)`
  1. forward는 왜 (1, 2) 형태를 기대하는가?
     - SimpleMLP.forward 내부 계산

       ```python
       def forward(self, X):
           self.z1 = np.dot(X, self.W1) + self.b1 # (1, hidden_size)
           self.a1 = self.preprocessor.activate_function(self.z1)

           self.z2 = np.dot(self.a1, self.W2) + self.b2 # (1, output_size)
           self.a2 = self.preprocessor.activate_function(self.z2) # 출력
           return self.a2
       ```

     - (원인) W1의 shape은 `(2, hidden_size)`이므로, "행렬 곱셈 규칙"에 따라 X는 `(1, 2)`여야 함.
       - W1의 shape은 preprocessor.initialize_weights 메서드에서 확인 가능

  2. reshape의 역할과 내부 파라미터의 의미
     - reshape는 배열의 형태를 바꾸는 함수
     - 예시

       ```python
       input = np.array([0, 0]) # shape
       input.reshape(1, -1)
       input.reshape(-1, 1)
       ```

       - `-1`는 나머지 차원을 자동으로 계산함을 의미

  3. 행렬(Matrix)란?
     - 선형대수에서 행렬은 숫자들의 직사각형 배열
       - 0차원 배열: 스칼라(Scaler)
       - 1차원 배열: 벡터(Vector)
       - 2차원 배열: 행렬(Matrix)

  4. 차원(Dimension)이란?
     - 배열이 몇 개의 축(방향)을 갖고 있는지를 의미
     - 예시
       |예시|차원|`shape(data)` 결과|설명|
       |-|-|-|-|
       |5|0차원|()|스칼라|
       |[5, 6]|1차원|(2,)|벡터|
       |[[5, 6]]|2차원|(1,2)|행렬(1행 2열)|
       |[[5], [6]]|2차원|(2, 1)|행렬(2행 1열)|

- (현상) python 동작 터미널 명령어를 실행했을 때, pyc 파일이 생기는 이유
  1. .pyc 파일이 무엇인가?
     - 해당 파일은 "파이썬 바이트코드" 파일
     - .py 파일 -> 사람이 읽을 수 있는 소스 코드
     - .pyc 파일 -> 파일썬이 이해할 수 있도록 컴파일된 중간 코드
     - (소결) 파이썬은 순수한 인터프리터 언어가 아니라, 컴파일 + 실행 과정을 거치는 하이브리드 형태
  2. `python main.py` 명령어를 실행했을 때 실제로 일어나는 일 (전체 흐름)
     1. 파이썬 파서로 main.py에서 AST 생성
     2. 컴파일러로 AST에서 바이트코드 생성
     3. 파이썬 가상 머신(PVM)으로 실제 실행
  3. AST란 무엇인가?
     - Abstract Syntax Tree의 약자로
     - py 파일을 컴파일러가 이해할 수 있도록 트리 구조로 변환된 결과
  4. .pyc 파일을 만드는 근본적인 이유
     - 파이썬 성능 최적화를 위해
     - py 파일을 실행할 때마다 파싱부터 컴파일 과정을 반복하면 느림
     - 한 번 컴파일한 바이트코드를 .pyc 파일로 저장해두고, 다음 실행할 때 컴파일 과정을 생략하고 바로 실행 가능
     - 특히 import 문으로 다른 모듈을 불러올 때 효과 극대화
  5. `__pycache__` 폴더가 생기는 이유
     - 소스 코드와 컴파일 결과를 분리해서 관리하기 위해 파이썬 3.3 버전부터 자동화
  6. (확장) 의도적으로 Git에 커밋하면 안되는 이유
     - 환경 의존적: pyc 파일은 파이썬 버전, 운영체제에 따라 다르게 생성됨
     - 용량 낭비: 바이트코드 파일이 불필요하게 커밋됨
     - 충돌 위험: 팀원마다 파이썬 버전이 다르면 pyc 파일이 계속 충돌 발생
     - 의미 없음: py 파일만으로 언제든 재생성 가능

## 회고 1

회고록: 신경망 구현에 있어서 객체 지향 vs 함수 지향 설계에 대한 고민
주제: 신경망 역전파 구현 시 OOP와 함수형 프로그래밍의 설계 차이와 데이터 흐름 추적

### What? (무엇을 경험하고 고민했는가?)

MLP를 NumPy로 직접 구현하는 과정에서 SimpleMLP 클래스 하나에서 forward, backward, 중간 활성화 값(self.z1, self.a1, self.z2, self.a2) 등을 모두 관리하는 구조로 코드를 작성

- 이 과정에서 다음과 같은 의문이 생김:
  - backward에서 self.a2 같은 값을 사용하는 것이 자연스러운가?
  - 함수형 스타일처럼 backward(self, X, output, y)처럼 명시적으로 값을 넘기는 것이 더 나은 설계가 아닐까?
  - 하나의 클래스에 모든 상태를 몰아넣으면 데이터가 어떻게 흐르고 업데이트되는지 파악하기 어렵기 때문
  - ANN에서 CNN으로 넘어가면서 Conv2D 같은 레이어를 분리해야 할까? 분리하면 흐름 파악이 정말 쉬워질까?

### So What? (그래서 무엇을 깨달았는가?)

이 고민을 통해 OOP와 함수형 프로그래밍의 근본적인 차이를 이해

- OOP의 강점: forward에서 계싼한 중간 활성화 값을 객체의 상태(self)로 저장하면, backward에서 별도로 전달하지 않아도 바로 사용 가능
  - 이는 코드가 간결해지고, 특히 레이어가 많아질수록 실용적
  - 각 레이어가 자신의 상태를 캡슐화하기 때문에 책임이 명확
- 함수형의 강점: 데이터 흐름이 명시적이나, 역전파의 경우, forward에서 계산한 모든 중간값을 파라미터로 반환하고 backward에 전달해야 하므로 코드가 길어지고 복잡 (특히 CNN처럼 구조가 복잡해지면 관리 비용이 급증)
- 하나의 거대한 클래스에 모든 것을 넣는 것은 **인지 부하를 증가**시킨다. 변수가 어디서 생성되고 어디서 사용되는지 추적하기 어렵기 때문이다.
- 레이어를 분리하거나 self.cache를 도입하는 것은 단순한 편의가 아니라, **데이터 흐름을 명시적으로 만들기 위한 설계 선택**이라는 점을 깨달았다.

### Now What? (앞으로 어떻게 할 것인가?)

- 단기적으로는 self.cache를 도입하여 중간 활성화 값을 한 곳에 모아 관리하는 방식으로 리팩토링을 진행할 예정. 이는 현재 구조를 크게 바꾸지 않으면서도 흐름 파악을 쉽게 만들어줄 것으로 기대
- 중기적으로는 Linear, Conv2D와 같은 레이어를 독립적인 클래스로 분리하는 방향 검토 예정. 각 레이어가 자신의 상태와 연산을 책임지게 하면, 전체적인 데이터 흐름이 더 명확해질 것으로 예상.
- 장기적으로는 함수형의 명시성과 OOP의 실횽성을 적절히 결합한 방식을 고려할 계획. 특히 CNN 구현에서는 레이어 분리가 더 큰 장점을 발휘할 것으로 판단.

### 본 회고 최종 정리

프로그래밍 설계 철학이 실제 소스 코드에서 어떻게 영향을 미치는지에 대해 깊이 생각해볼 수 있는 계기가 되었습니다. 구체적으로, OOP가 역전파 구현에서 실용적인 이유와 함수형이 갖는 명시성의 가치 사이에서 균형을 찾는 것이 중요하다는 점을 배웠습니다. 의도와 흐름이 명확한 코드 작성을 위해 설계 선택의 이유에 대해 고민하고 설계하는 노력을 다짐했습니다.
